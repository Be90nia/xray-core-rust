## dct2d（P0）packet-up body 无上限整读 → 按 ContentLength 预检 + 限读

**改了什么**
- `src/hub/handler.rs:558` `extract_packet_payload(req, ctx, max_body)`：新增 `max_body` 形参。
- `src/hub/handler.rs:594` `content_length(headers)`：Go `hub.go:290` 的 `request.ContentLength > scMaxEachPostBytes → 413` 预检（缺失/非法 → 走限读路径）。
- `src/hub/handler.rs:606` `read_body_limited(body, max)`：逐帧读 body，**每次读之前**判「本次读会不会越界」，越界即 413。等价 Go `io.LimitReader(body, max+1)` + 事后判长的结果语义，但峰值驻留 = `max`（不是对端声明的 2 GB）。
- `src/hub/handler.rs:297` `handle_packet_up` 把 `ctx.sc_max_each_post_bytes` 传下去；原有「合并 payload > max → 413」终判保留（Go `hub.go:320`）。

**为什么这么改**：旧实现 `body.collect().await` 后才在 `handle_packet_up` 判长——2 GB body 会整读进内存再丢弃。实测基线 `dist/xray.exe` 推 2 GiB：
content-length 形态 RSS 13.3 MB → **3483.9 MB**；chunked 形态 13.2 MB → **4306.3 MB**（见 §e2e）。

**验证**
```
cargo test -p xray-transport-splithttp hub::handler::packet_up
```
- `packet_up_oversized_content_length_rejected_before_read`：`Content-Length: 2000000000` → 413 且 body 读字节数 = **0**
- `packet_up_body_read_stops_at_limit`：可用 3 MiB、上限 1 MiB → 413，实际读 ≤ 1 MiB + 一块
- `packet_up_body_exactly_at_limit_accepted`：正好 1 MiB → 收（不误伤）
- `packet_up_combined_payload_over_limit_rejected`：1 MiB + 1 B → 413
- wire 侧（`tests/hub_limits.rs::packet_up_oversize_content_length_is_413_without_body`）：真实 listener，客户端**一个 body 字节都没发**即收到 `413`

## 3zbwx（P1）SessionMap 无容量门 + session id 客户端自选

**改了什么**
- `src/hub/session.rs:46-75`：新增 `DEFAULT_MAX_SESSIONS = 1024`、`MAX_SESSION_ID_LEN = 128`、`SessionUpsertError::TooManySessions`、`is_valid_session_id()`（非空 + ≤128 + 可打印 ASCII；**不约束具体字符集**，因为 `sessionIDTable` 允许客户端自定义任意 ASCII 字母表）。
- `src/hub/session.rs:112` `upsert → Result<Arc<HttpSession>, SessionUpsertError>`：慢路径 lock 内先判 `map.len() >= max_sessions` 再插入；**已在表的 id 不受门影响**（满了以后正常会话仍可用）。
- `src/hub/handler.rs:147`：id 校验门（`dispatch_validated` 内，padding 之前）→ 非法即 `400` + WARN 日志。
- `src/hub/handler.rs:798` `session_error_response()`：表满 → `429 Too Many Requests` + WARN 日志（fail-visible，不静默丢弃）。
- 三处 upsert 调用（packet-up / stream-up / stream-down）全部接错误分支。

**与 Go 的行为差异（必须显式登记）**：Go `hub.go` 不校验 session id 形状/长度，Rust 现在拒绝
「空以外的非法形状」「>128 字节」。默认 UUID 36 B、自定义 `sessionIDTable` 常规长度都远小于 128，
不受影响；只有把 `sessionIDLength` 配到 >128 的极端客户端会拿到 400。选 128 而不是无界，是因为
id 长度完全由对端决定（path/query/cookie 都带），超长 id 会把每条请求的键分配放大到对端可控规模。

**为什么 1024**：单客户端正常只占 1 条会话；1024 覆盖「CDN 汇聚大量客户端」的合法聚合，同时把无界增长钉死（每条会话含 UploadQueue）。30 s reap 之前最多 1024 条。**与验收文案的差异**：票面验收写「伪造 200 个不同 session id → 达到上限后明确拒绝」，1 条请求=1 条会话时 200 远未到 1024；实测门限在 **第 1025 个新 id** 触发（见下）。若 PM 要求「200 个即触发」，把常量改小即可（`DEFAULT_MAX_SESSIONS`），但会把合法并发客户端挡在门外——请 PM 拍板数值，代码结构不受影响。

**验证**
```
cargo test -p xray-transport-splithttp hub::session
cargo test -p xray-transport-splithttp hub::handler::session
cargo test -p xray-transport-splithttp --test hub_limits session_gate
```
- `upsert_rejects_new_ids_over_capacity`：cap=2，第 3 个新 id → `TooManySessions`，已存在 id 仍 Ok，被拒 id 不落表
- `session_id_validation`：UUID 与 `abc123!@#` 放行；空 / 129 B / 含 `\n` 拒
- `oversize_session_id_rejected_400` / `printable_session_id_accepted` / `session_table_full_rejects_new_ids_with_429`
- wire 侧（真实 listener，h1 keep-alive 单连接灌 1024 个不同 id 全 200）→ 第 1025 个 **429**；已有 id 仍 200

## 1fm1l（xhttp 半，P2）上行逐块新分配 → 复用块池

**改了什么**
- 新增 `src/pool_stream.rs`：把原 `hub/dl_stream.rs` 的池（`BufPool` / `PooledBuf` / `Bytes::from_owner`）泛化成 `PoolStream<R>`（`AsyncRead → Stream<Item = io::Result<Bytes>>`），块大小作参数。
- `src/hub/dl_stream.rs`：`DlStream` 退化为「`PoolStream` → `Frame::data`」薄包装，保留 `XHTTP_SRV_SEND` 站点归因。
- `src/dialer.rs`：5 处 `ReaderStream::new(pipe_server)` → `PoolStream::new(pipe_server, UPLINK_CHUNK)`；5 处上传 pipe `duplex(8192)` → `duplex(UPLINK_CHUNK)`（4 KiB→64 KiB，DAT A 帧数/唤醒数降 ~16×）。
- `src/pool_stream.rs:24` `UPLINK_CHUNK = 64 KiB`（= 服务端 `DUPLEX_BUF`）。

**为什么这么改**：`tokio_util::io::ReaderStream` 用 `BytesMut::split` 把容量留在帧里，下一次 `poll_next` 只剩空 `BytesMut` → 每帧重新 `reserve`（缺省 4 KiB）。树内已有 bd 9eu4a 的下行孪生（`dl_stream` 实测把 srv 发送从 1.06 MB/MB 打下来），上行同根因，直接泛化复用而不是再写一份。

**验证**：见 §e2e 的 alloc/MB 前后对比（`XRAY_ALLOC_STATS=1`）。
```
cargo test -p xray-transport-splithttp pool_stream
```
- `frames_carry_all_bytes_in_order_and_blocks_return_to_pool`：字节序完整
- `blocks_are_recycled`：块归还池（否则=逐帧重分配）
- `dialer::dial_reality_stream_one_sends_data_immediately_after_headers`（既有回归守卫）仍绿——上传 pipe 变大**不引入** DATA 帧延迟

## 2xgln（P2）服务端并发流无上限 → SETTINGS_MAX_CONCURRENT_STREAMS

**改了什么**
- `crates/xray-transport-splithttp/src/transport.rs:84-90`：`H2_MAX_CONCURRENT_STREAMS = 250`；`serve_http_conn` 的 hyper-util auto builder `.http2()` 链加 `.max_concurrent_streams(250)`（h1/h2c 与 h2-over-TLS 共用）。
- `crates/xray-transport-grpc/src/transport.rs:40-47` `H2_MAX_CONCURRENT_STREAMS = 250`；`accept_h2` 的 `server::Builder` 加同项。

**为什么 250**：Go splithttp hub 用 `http.Server` + `SetUnencryptedHTTP2(true)`，其 x/net/http2 服务端缺省 `MaxConcurrentStreams = 250`。文档化差异：Go **grpc-go** 服务端缺省是 MaxUint32（不设上限），Rust 取 250 属加固；该值只发在 SETTINGS 里，对端（grpc-go / Rust h2 client）按 SETTINGS 排队，互通语义不变。

**验证**（raw h2 客户端——只有忽略 SETTINGS 才能越限）
```
cargo test -p xray-transport-splithttp --test hub_limits h2_rejects_streams_past_max_concurrent
cargo test -p xray-transport-grpc h2_server_advertises_and_enforces_max_concurrent_streams
```
- 服务端 SETTINGS 中 `SETTINGS_MAX_CONCURRENT_STREAMS(0x3) = 250`
- 连开 251 条 HEADERS（不带 END_STREAM，流保持活跃）→ 第 251 条（stream id 501）收到
  `RST_STREAM(REFUSED_STREAM=7)`
- 对照 `single_raw_h2_request_is_accepted`：单流正常 200（证明 raw 客户端本身合法，失败可归因）

## 6. 遗留 / 需 PM 拍板

1. **3zbwx 会话上限数值**：实现取 `DEFAULT_MAX_SESSIONS = 1024`（生产安全），票面验收文案的
   「伪造 200 个」在本值下不会触发。若要「200 即触发」请改常量（结构不变），但会挡合法并发客户端。
2. **预置缺陷（非本组引入）**：`h3/stream-one` 在 **Rust 服务端**回空（`curl (52)`）；
   基线二进制同脚本同两条失败，本组未改该路径。建议单独开票。
3. **与 Go 的有意差异**：① session id 形状/长度校验（Go 无）；② 会话数上限（Go 无限）；
   ③ grpc 服务端 `SETTINGS_MAX_CONCURRENT_STREAMS = 250`（Go grpc-go 缺省 MaxUint32）。
   三者都不改变正常客户端互通（互通矩阵已证）。
4. **未做**：`stream-up` 单块大小上限（Go 同样不设，body 走 `into_data_stream` 已有 h2 流控兜底）；
   h3 服务端并发流上限（QUIC，票面只点 h2 两处）。
