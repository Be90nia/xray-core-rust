| 字段 | 内容 |
|---|---|
| 严重度 | **P1 high** |
| crate | `xray-proxy-ss` / `xray-proxy-trojan` / `xray-proxy-vless` |

#### P1-004：AUDIT-SEC-004 — 整数截断：chunk size u16 溢出静默替换为 u16::MAX

| 字段 | 内容 |
|---|---|
| 严重度 | **P1 high** |
| crate | `xray-proxy-vmess` / `xray-proxy-vless`（encoding）|
| 文件:行号 | `crates/xray-proxy-vmess/src/dispatcher.rs:608` / `crates/xray-proxy-vmess/src/aead/mod.rs:285,298` / `crates/xray-proxy-vmess/src/inbound/server.rs:498,521,559` / `crates/xray-proxy-vmess/src/encoding/body_chunk.rs:298,509` |
| 标题 | 多处 `u16::try_from(...).unwrap_or(u16::MAX)` 静默截断 → 收侧误读 |
| 描述 | VMess chunk size 在加密后 + padding 后计算，整数超 u16 (65535) 时静默替换为 `u16::MAX`，**收侧解码按 u16::MAX 取后续 65535 字节，但实际数据 > 65535 字节，剩余字节进入下一轮 chunk 解析**——此语义与 Go 完全一致，但 `unwrap_or(u16::MAX)` 形式掩盖了协议违规，不易被安全审计发现。攻击者（出站端）若构造超长 chunk：a) 收侧解析错位导致内容错位但无错误（静默数据腐败）；b) 在某些路径触发无限循环（见 30gf 压测的"分钟级摆动=路径 regime"反例） |
| 影响 | 1) 静默数据腐败（无错误返回）；2) 与 Go 语义一致但实现选择"宽进严出"反向——应 hard error 而非静默替换；3) 安全审计易忽略 |
| 建议 | 改为 `u16::try_from(...).map_err(|_| VmessError::ChunkSizeOverflow)?` —— 协议层任何超限都是攻击/编程错误，应早 fail |
| 复现 | `cd D:/Project/Xray-core-rust && grep -n "u16::try_from.*unwrap_or(u16::MAX)" crates/xray-proxy-vmess/src/` 见 7 处；构造 encrypted_size + padding_size > 65535 的 chunk，调 `encode_chunk_stream` 见无 Err 返回 |
