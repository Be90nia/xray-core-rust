### 1.2 两案权衡

**方案一：违宪需修（切层）**

| 形态 | 内容 | 代价 |
|---|---|---|
| 全引擎下沉（声明原设问） | quic 引擎（session/quinn 封装）下沉公共层 | **过重**：hysteria/splithttp 根本没用 quic crate 的 session 层（实测各自直连 quinn），下沉无处可沉、无收益 |
| **窄切层（推荐形态）** | 仅把 `congestion_swappable`（BBR/Brutal + quinn_bridge CC 槽位）切出兄弟命名空间（新底座 crate，或并入引擎层命名），xray-transport-quic 保留 quic 协议血肉 | 机械改动：1 模块搬家 + 3 个 Cargo.toml + 少量 import，半天级，零行为风险；代价是 crate 数 +1 |

修的硬理由：零边令的存在理由是"**无边即无法走私类型**"——今天 `HysteriaCCSlot` 这个具体类型正经兄弟边穿越（splithttp 持有 quic crate 的具体类型），正是条文点名的危害实例。且宪法自身的翻转哲学（"重新切层不堆豁免"）指向给底座一个家，而不是记一笔永久豁免。

**方案二：豁免登记（合理复用）**

- 依据：T0.5 豁免机制是宪法**自带的合法通道**（理由+复评日期）；且 3-5 号边若按性质改挂 dev-dep、6 号删除后，真正需要豁免的只剩 2 条 < 5 条翻转阈值——**不触发**宪法自身"重新切层"条款。
- 代价：零代码改动；但 (a) T0.5 未落地前豁免台账无执法背书，属"有法无门"状态的口头和解；(b) `congestion_swappable` 是半天可断的边，动用豁免这个为"难断之边"设计的机制，是制度浪费；(c) 底座 API 耦合会随 H3/CC 演进静默生长，复评日期是软约束。

### 1.3 架构裁决

**裁决：修（窄切层形态），豁免仅作过渡台账。**

### 2.3 ② 16/32MB 每连接窗口内存代价估算

机制事实（registry 源码）：窗口是 SETTINGS **计数器，不预分配内存**；收侧缓冲按 DATA 到达惰性增长，单连接聚合上限 = **连接窗 32MB**（流窗 16MB 只约束单流；hyper server `max_concurrent_streams` 默认 200，proto/h2/server.rs:69——200 流 × 16MB 的放大被 32MB 连接聚合窗封死，语义健康）。send 侧上限 = max_send_buf_size。

| 场景 | 每连接代价 |
|---|---|
| 空闲/轻载连接 | KB 级（窗口仅计数器） |
| 单重载流稳态 | 在途 ≈ BW×RTT ≈ 40MB/s×0.15s ≈ **6MB**（非 48MB） |
| 单连接理论天花板 | server：32(收)+16(发，已上线)=48MB；client：16(发，提案)+32(收，已设)=48MB；端到端单流双端 ≈96MB |
| 恶意扇出 | N 连接 × 各自打满：100 连接 ≈ 3.2-4.8GB → 小内存 VPS OOM 风险。**跨连接无全局闸**，这是唯一真实风险面 |

**结论**：用户场景（个人 VPS、单用户自用、低并发重流）常数 16/32 完全可接受，**无需按连接数自适应**（adaptive 同天花板见 ③，且收窗空闲本就不占内存——自适应省的是虚构的）。多租户/公网裸暴露前再上配置闸，落点即宪法 §6.4 第 15 项 `tuning()`（TuningSnapshot），与用户"频繁调用的进框架"偏好同构——**不阻塞本票**。

### 2.4 ③ adaptive_window(true) 替代方案分析

源码事实：`adaptive_window(true)` 会**覆写**两窗为 `SPEC_WINDOW_SIZE = 65,535`（hyper server/conn/http2.rs:183-195 + proto/h2/mod.rs:30），然后靠 PING 探测 BDP 爬坡（ping_delay 100ms，ping.rs:51），**硬上限 `BDP_LIMIT = 16MB`**（ping.rs:364）。且与 `initial_*_window_size` 互斥（setter 置 adaptive_window=false，:158-159；文档明言 override）。

| 维度 | 固定 16/32MB | adaptive_window(true) |
|---|---|---|
| 饱和吞吐天花板 | 16MB | **相同**（BDP_LIMIT=16MB）——零收益 |
| 起步行为 | 首字节即满窗 | 64KB 起爬坡，需持续流量 + 多个探测周期（100ms 间隔 × RTT） |
| 对短命流/测速 | 稳定满速 | **爬坡未完成即结束 → 测速低估/抖动**（用户唯一验收方法 = v2rayN 短窗多线程测速，此为硬伤） |
| grpc 裸 h2 现场 | 直接可用 | **h2 crate 无 adaptive** → 两套心智模型 |
| send 侧 | max_send_buf_size 独立设 | adaptive 不覆盖 send 侧，仍需单独设 |

**裁决：固定 16/32 为主方案**；adaptive 仅作"实测 RSS 压力出现后"的 fallback 备选，且因测速爬坡抖动 + grpc 无法统一，不推荐替换。

### 2.5 ④ 其它副作用排查

- **QUIC 路径**：零交互。quinn 族限流窗独立配置（quinn_adapter.rs:306-313 已对齐 Go 语义），hyper/h2 setter 不触 quinn；两条兄弟边（congestion_swappable）与 h2 窗口无关。
- **h1 协商**：setter 全部只作用于 h2 路径，auto builder 的 h1 分支无流控概念，不受影响。
- **慢客户端/慢上游**：send buf 16MB（server 侧已上线）意味着对端停滞时最多缓冲 16MB 后背压——有界，可接受；提案(2) 使客户端侧对称（用户 PC 内存，无虞）。
- **应用层缓冲交互**：splithttp handler 自有 `max_buffered_posts`/`sc_max_each_post_bytes` 上界（hub.rs:198-201 HandlerContext），h2 窗放大不破坏应用层限额，二者独立叠加。
- **内核层**：纯用户态缓冲，与 SO_RCVBUF/rmem（88m0 战役层）无耦合，无回归面。
- **文档 nit（顺带）**：dialer.rs:559 注释称客户端默认 max_send_buf 400KB——registry 源码实证**客户端默认 1MB**（hyper proto/h2/client.rs:51），400KB 是 server 默认；建议随批修正注释。
