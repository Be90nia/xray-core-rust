## 票 2：n43f（P1）mux frame u16 saturate → 显式 error

### 定位（比审计更进一步）
`crates/xray-mux/src/frame.rs:516-519`（原）`content_len.try_into().unwrap_or(u16::MAX)`。行为探针实证：`write_target_to_vec` 内 `Buffer::with_capacity(32)` + `Buffer::write_from`（xray-buf buffer.rs:235 只写 `free()` 内的量）**静默截断超长域名**——40 000B 域名只写出 ~28B，body 永远 <512，u16 饱和分支实际不可达；真正风险是截断后 domain len 字段与数据不符 → 对端解析错位 → 永久 desync（审计 interop F5 主场景同源）。

### Go 基准
- 读路径 `common/mux/frame.go:119-121`：`if metaLen > 512 { return errors.New("invalid metalen") }`（512 硬顶是策略）
- 写路径 Go 靠 buf 容量结构性顶住；Rust Vec 无界，需显式检查

### 修复（三道闸，全部 `MuxError::MetadataTooLong`）
1. `write_target_to_vec`：域名 >255（u8 len 前缀装不下）报错
2. `write_target_to_vec`：按地址实际线格式精确预分配（port 2 + type 1 + 4/16/1+len），杜绝 Buffer 截断
3. `to_bytes()` 签名 `Vec<u8>` → `Result<Vec<u8>, MuxError>`：总长 >MAX_METADATA_LEN(512) 报错（`write_to` 传播，签名不变）

调用方迁移：`to_bytes()` 生产调用仅 `write_to`；测试调用 18 处（frame.rs 12 + worker.rs 2 + integration.rs 4）加 `.unwrap()`，断言内容零改动。

### 红→绿
- 红①（截断实证）：修复前探针测试 `declared == actual` **通过**（40KB 域名被截断静默 Ok）——证明截断存在且长度字段一致（对端按截断数据错位解析）
- 红②（编译）：新测试 E0599（`Vec<u8>` 无 `expect_err`）——旧签名不兼容
- 绿：`test_to_bytes_oversized_meta_errors`（300B 域名 → MetadataTooLong）、`test_to_bytes_total_over_512_errors`（255+255 双满 → MetadataTooLong(538) > 512）、`test_to_bytes_domain_255_boundary_ok`（255B 合法边界完整写出不误伤）全过
