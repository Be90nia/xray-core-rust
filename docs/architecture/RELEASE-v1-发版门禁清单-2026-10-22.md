# RELEASE-v1 发版门禁清单（2026-10-22）

> **背景**：框架重构（xray-frame P0-P3，估 6-12 周）会重写装配层/配置层/核心 API，重构期不适合发版。
> **因此**：在重构开工前，先把当前能力封成一个**可发版的稳定版**（RELEASE-v1），范围 = 已闭环能力 + 低返工增量，**不含任何框架期项**。
> **性质**：本文件是**门禁清单**（可执行 + 有判定标准），不含代码实施。每次发版复用，版本号递增。

## 0. 三条不可破的前提

1. **wire 不变**：Go↔Rust 协议字节布局不得变（任何改动必须有互通证据）。
2. **不在框架重写的层上新增功能**：落在 P0-P3 重写范围（装配层/配置解析/核心 API）的项一律留到框架期（见 §1.2）。
3. **可追溯**：每个发布产物必须能自证是哪个 commit 构建的（`identity` 日志含 `git_rev` + `exe_fingerprint`；`VERSION_Z` 恒定 26.10.10 不足以区分构建，必须 bump）。

## 4.3 VPS 互通实测（2026-10-22 夜，VPS-US1）

**编排脚本**：`reports/release-v1/vps_interop.py`（复用 `dist/interop_ci.py` 的 `build/build_x` 配置构建器，改远端地址；验收目标 = VPS 回环 `python3 -m http.server` 的 marker 文件，故**不依赖外网**但走真公网往返）。

**关键环境事实（踩坑，必记）**：
1. **176 的 `iptables INPUT policy DROP` + ufw 白名单只放 443/8443/SSH(SSHPORT)** → 任意端口（12829+）从外部不可达（实测 8s 超时）。**改防火墙属红线，不碰**；改用 `ssh -L` 隧道把本机端口映射到 VPS 回环（脚本默认 `--via-tunnel`，`--no-tunnel` 可关）。
2. 公网 IP 上 **Go 拒绝「无 TLS 的 vless/vmess/trojan」**（`infra/conf` 校验：“unless the server address is a private IP or domain”）；脚本对 ws/splithttp/grpc 自动补 TLS + 证书 pin（SNI=localhost 与证书 CN 一致）。
3. 远端 echo 必须**启动后校验**（`curl` marker 命中才继续），否则会得到成片 “Empty reply from server” 的假失败。
4. 只在 `/tmp/vpsi`（VPS）+ `target/vps_interop`（本机）建临时文件、只用临时端口，**不碰**现役 `/root/agsbx` + systemd `xr.service`（pid 9979 全程未动）；每例结束 kill 服务端 + 删远端目录。

**已跑方向：Go 服务端（VPS）+ Rust 客户端（本机）—— 8/8 PASS**

| 协议 | 结果 |
|---|---|
| vmess / vless_vision_tls / trojan_tls / vless_ws | PASS ×4 |
| ss / ss2022 | PASS ×2 |
| splithttp / grpc | PASS ×2 |

（对照组 `go_srv->go_cli` vmess+vless_ws 也 PASS，证明 harness 本身无系统性假失败。）

**待跑（需 CI 产出的 Linux Rust 二进制）**：`rust_srv->go_cli`、`rust_srv->rust_cli`（含 reality/hysteria2/anytls/tuic 等 Go 无客户端的 Rust-only 协议）。

## 4.4 G8 性能基线实测——**PASS（SSE4 定稿，147-170 MB/s）**

同机、同工具（`tools/loopback_alloc_bench.py`）、同一份 bench 配置、各 3 轮：

| 构建 | 吞吐（MB/s） | 说明 |
|---|---|---|
| `dist/xray.exe`（2026-10-13） | 165.4 / 183.8 / 175.4 | 与 `docs/benchmarks/baseline.md`（154-167）同档 |
| 当前构建 `target/release/xray.exe`（`.cargo/config.toml` → `target-cpu=x86-64`） | 37.8 / 39.1 / 39.2 | **-77%** |
| 同代码 `CARGO_BUILD_RUSTFLAGS=-C target-cpu=native` | 159.4 / 183.1 / 189.1 | 与基线同档 |

**根因**：`target-cpu=x86-64` 关闭 AES-NI / SHA / PCLMULQDQ 等扩展 → 加密链走软件实现。`.cargo/config.toml` 于 2026-10-20 按 bd hxy3 裁决撤销 native（当时的理由是「native 5 倍慢」，与本夜实测相反），而基线数字是 native 期采集，钉 x86-64 后**从未复测**。

**影响面**：CI release 构建同配置（`release.yml` 的 `RUSTFLAGS: ""` 使 config.toml 的 rustflags 不生效，等于默认 x86-64）→ **发版产物即 4.5x 慢**。

**处置（用户 2026-10-22 拍板「修吧」→ 方案 B）**：`.cargo/config.toml` 改为 `[target.'cfg(target_arch = "x86_64")']` 分目标声明
`-C target-cpu=x86-64 -C target-feature=+aes,+pclmulqdq,+sse4.1,+sse4.2,+popcnt`（2010 年后 x86-64 普及特性；aarch64/arm 交叉编译不命中该 cfg）。
同时删除 6 个 workflow 里的 `RUSTFLAGS: ""` 空覆盖（否则 config.toml 被完全压制，CI 产物仍慢）。

**修复后实测（同机同工具）**：157.9 / 178.1 / 173.6 MB/s → 与基线同档。

**⚠️ 下面这段结论已被推翻（2026-10-23 01:30 更正）**：vision 的失败率差异**不是 SSE4 造成的**，而是我早期脚本泄漏在 VPS 12829 上的 vmess 僵尸服务端 `SO_REUSEPORT` 分流（~50%，按源口哈希成串）。清掉僵尸后同一二进制 vision **10/10**、Go 对照 8/8。故 s3uu 的「SSE4 劣化正确性」结论**作废，需在干净端口重测**；性能方案（f39e）也可能安全，待重测后恢复。

**最终结论（2026-10-23 02:1x，干净端口 12840 复测）**：SSE4 配置 **安全** —— 纯 x86-64 与 SSE4 各 5/5 PASS；
性能 **147.1 / 170.2 / 169.5 MB/s**（纯 x86-64 为 37.8-39.2），已恢复并在 master（`d31a1f94`）。
s3uu **关闭（结论作废：真因是 VPS 12829 僵尸服务端分流）**；f39e 随之关闭。
兼容性：SSE4.2+POPCNT = Win11 硬要求，安全；仅 2008 年前 Core 2 级机器有 SIGFAIL 风险。
