# bd zct77 · xhttp(h2) 高 RTT 吞吐失速 —— 方案

- 日期：2026-11-09
- 状态：**定稿 v1**（待 `reports/2026-11-09-zct77-h2-flowcontrol-research.md` 的外部先例补入 §11）
- 前置证据：`reports/2026-11-09-xhttp-rtt-stall-fix.md`（C1-C6 根因链）、`reports/2026-11-09-zct77-design-options.md`（oracle 方案咨询）
- 范围：只谈**吞吐失速**（RTT 依赖）；C4 静默断流是另一个缺陷，另有单（根因已定位：bridge 半窗布防点错位）

## 1. 结论先行

1. **「流控/退款策略是主因」这个假设，被算术否掉了。** 维持 7.77MB/s 只需 2.39MB 在途；而 h2 的窗地板 = `32MiB − 11.18MiB ≈ 20.8MiB`，是需求的 **8.7 倍**。所以调窗常量、改退款粒度都不会动 7.77（与「10 组窗扫描全平」自洽）。
   > **⚠️ 但 `H2FlowResearch` 给出一个能反驳这条的机制（详见 §11.1）**：h2 的 `capacity = min(窗余量, max_send_buf − buffered)`，**buffered 顶满 16MiB 时 capacity 就是 0，与窗余量无关**。⇒「窗余量充足」不等于「发送端有容量」。两份独立分析在此**直接冲突**，裁决者是 **E4**（缩 send_buf 变好还是变坏），不是投票。
2. **两边单独都不慢，坏在「双 h2 自配对」。** 同一台 ours-srv 配 Go 客户端 9.63 ≈ Go-srv 9.74（打平）；同一台 ours-cli 配 Go-srv 14.9（最快）。只有 ours↔ours = 7.77（最慢）。
   > **⚠️ 2026-11-09 更正（`H2FlowResearch` 源码取证）**：C≈D 的「打平」**不能**用来证明 ours-srv 没问题——**Go 客户端默认收窗只有 1MiB/流窗 4MiB**（`x/net/http2/config.go:104-113`），C/D 两格都是被**客户端小窗**绑定，服务端差异被掩盖。⇒ 真正有效的对照只有 **A(7.77) vs B(14.9)（同一 ours 客户端、不同服务端）**，这两格的 1.9× 差**只能归 ours-srv**。§1.2 原表述作废，其余结论不变。
3. **当前最强的可检验假设**：服务端「灌满 16MiB 发送缓冲 → socket 只吃 ~2.4MB → 排空后等 1 RTT → 再灌」的**停-启相位**，叠加内核 autotune 只在「连接真正跑满」时才长窗 ⇒ 形成**低窗双稳态**（快轮 14.48 / 慢轮 7.77 可能是同一系统的两个稳态，而不是 rig 噪声）。
4. **下一步不是改代码，是做 E1+E2+E4 三个零代码实验**（合计 ~65 分钟），用互斥预测把「流控 / 应用写侧 / 内核 socket 窗 / rig」四层钉死，再决定改哪一层。**先 fork h2 是最贵的错**（15 分钟的问题变成两周的问题）。
5. 「比 Go 好的原创设计」（低水位退款 + BDP 自适应）**成立但不属于本票**：它对 zct77 的预期收益为 0（E5 会证），应作为**独立健壮性项**立项，触发条件是出现 `窗 < 1.5×BDP` 的部署（例如 200MB/s × 0.3s = 60MB BDP）。

## 2. 事实基线（实测，非推测）

测试台：lo hairpin + netem 双向 150ms（RTT≈308ms），100MB，本地 origin。

| 格 | 客户端 | 服务端 | 吞吐 | 耗时 |
|---|---|---|---|---|
| A | ours | ours | **7.77 MB/s** | 12.87s |
| B | ours | Go | **14.9 MB/s** | 6.71s |
| C | Go | ours | 9.63 MB/s | 10.89s |
| D | Go | Go | 9.74 MB/s | 10.77s |

- 0ms 时 ours 反而更快（64 vs 50 MB/s）⇒ 非每字节开销，是「等」。
- strace：服务端 sendto 每 ~1.1MB 一簇（**该数是抽样，不是平均**），簇后整停 ≈1 RTT。
- 缺口量级：`(12.87−6.71)/0.308 = 20` 次满 RTT 停顿 ⇒ **平均每 5.0MB 停一次**、停顿占比 48%。任何机制解释必须对上「~5MB 一周期」（≈ 16MiB 缓冲的 1/3 ≈ 0.64s ≈ 2 RTT）。
- 写隙三联状态：h2 内部囤满 16.6MB + 连接窗尚余 16.7MB + 内核报 `app_limited`（写队列空）。
- client 侧 `release_capacity` 调 6458 次（105.5MB 全量），WU 以 ~11.18MB/笔、约 2.2s 一笔到达。

## 3. 机制：三条一手事实（源码级）

| # | 事实 | 位置 |
|---|---|---|
| M1 | h2 接收侧退款阈值 = **对端已知剩余窗 / 2**，满足即**一次退全部**（⇒ 窗地板 2W/3，笔 W/3） | `h2-0.4.20/src/proto/streams/flow_control.rs:93-110` |
| M2 | Go 接收侧退款阈值 = **固定小值** `inflowMinRefresh`（4KB 级）或「至少翻倍对端可用窗」⇒ 细粒度 | `x/net@v0.61.0/http2/flow.go:31-52` |
| M3 | h2 **没有** `adaptive_window`（全 crate 扫描 0 命中；只有 5 个静态旋钮）。前班报告「hyper adaptive_window 排除」一句**不成立** | h2 0.4.20 全源扫描 |
| M4 | h2 每流 `capacity = min(发送窗, max_send_buf − buffered)` ⇒ **buffered 顶满 16MiB 时 capacity=0，应用侧硬停** | `h2/src/proto/streams/stream.rs:275-280`、`send.rs:297-360` |
| M5 | hyper 服务端 h2 body 泵：**`capacity()>0` 即整块 64KiB `send_data`**，不按 capacity 切分、不做突发整形、不额外 flush | `hyper-1.10.1/src/proto/h2/mod.rs:146-215` |
| M6 | hyper 客户端 h2 响应体 **把 DATA 帧交给调用方的那一刻就 `release_capacity`**（不等下游消费） | `hyper-1.10.1/src/body/incoming.rs:244-245` |
| M7 | 要更换退款策略**只能 vendor h2**（`release_capacity` 只动 `available`；WU 决策在 crate 内 `unclaimed_capacity`，调用点 `recv.rs:489`/`recv.rs:1158`） | 同上 |
| M8 | 本仓已有 vendor patch 先例（`vendor/rustls` 1.8M、`vendor/quinn-proto` 1.1M）⇒ 代价可估：复制副本 + `[patch.crates-io]` + 月度 rebase | `vendor/` |

## 4. 定量推理

**4.0 配对交互（最强线索）** —— 见 §1.2：ours-srv 与 Go-srv 在 Go 客户端下打平；ours-cli 比 Go-cli 更快；只有双 h2 自配对塌。

**4.1 窗量级核算**

| 目标吞吐 @RTT 0.308s | 所需在途 |
|---|---|
| 7.77 MB/s（实测） | **2.4 MB** |
| 14.9 MB/s（Go 服务端） | 4.6 MB |
| 50 MB/s | 15.4 MB |
| 100 MB/s | 30.8 MB |

服务端：流 16MiB / 连 32MiB / send_buf 16MiB；客户端 32/32/16MiB。
⇒ 稳态在途 2.4MB ≪ 窗地板 20.8MiB ⇒ **窗不是约束，调窗不是杠杆**。

**4.2 自增强双稳态假设（待 E2 判定）**
「连接窗有余量 + h2 缓冲顶满 + 内核 app_limited」三者同时成立，只有一种结构能给出：应用灌满 16MiB → socket 每次只吃 ~2.4MB → 排空后等 1 RTT → 再灌；autotune 只在连接真跑满时长窗 ⇒ 锁在 2.4MB。
预测：**慢轮的 `ss -ti` 的 rcvbuf/sndbuf 显著小于快轮**（若成立，7.77/14.48 是双稳态不是 rig 噪声）。
四格自洽性：B（Go-srv 3.8KB 稳态细写 ⇒ 不断供 ⇒ 窗长起来 14.9）；A（我方突发 + 客户端 10.7MB 才戳一次 ⇒ 双重不利 7.77）；C（我方突发但 Go 客户端约 2MB 戳一次 ⇒ 停顿被截短 9.63）。

## 5. 判别实验（全部零代码或 1 行，先测再改）

**总规矩**：同轮内 A/B 交错，每档 ≥3 轮，报**中位吞吐 + 失速秒占比**（按秒切片，`< 0.3×中位` 记失速）；每轮后 `tc -s qdisc show dev lo`，`drops/overlimits > 0` 该轮作废；离散 >15% 判 CONTAMINATED。

| # | 实验 | 时长 | 互斥判据 ⇒ 结论 |
|---|---|---|---|
| **E1** | 客户端设 4MiB 流窗（`XRAY_H2_FLOW_WINDOW_OVERRIDE_BYTES=4194304`），64MiB 作对照 | 15 min | A→**≥12MB/s**：流控确是约束（R4/R5 有救）；A→**≈9.6**：瓶颈是服务端写侧停-启（直奔 R1/R6）；A→**7.8±15%**：流控排除，否决 R4/R5 |
| **E2** | `ss -tinm` 0.1s 采样 + `tc -s qdisc` 前后对比 | 20 min | stall 期 `wmem≈0` + app_limited ⇒ 应用没交给内核（R6/R1）；`wmem` 满 + `rwnd` 大 ⇒ sndbuf 自锁（R3+R1）；`rwnd≈0` ⇒ 客户端侧；**快轮 rcvbuf/sndbuf ≫ 慢轮 ⇒ 双稳态成立**；qdisc drops>0 ⇒ rig 是主因，A/B 作废 |
| **E3** | 服务端 pcap，看 20 个突发起点前 2ms 内有无客户端 h2 帧（WU/PING/HEADERS） | 30 min | ≥80% 突发紧跟入站帧 ⇒ 唤醒饥饿（R6）；≤20% ⇒ 纯 ACK 驱动 ⇒ R4/R6 作废 |
| **E4** | `XRAY_H2_SEND_BUF_OVERRIDE_BYTES ∈ {2M, 5M, 16M}` × 3 轮 | 30 min | 2M/5M ≥ 16M×1.15 ⇒ R1 有效（落 1 行常量）；单调**下降** ⇒ R1 方向反了（唤醒成本是主项）⇒ 转 R6 |
| **E5** | 用已有慢轮数据算窗地板（`32MiB − max WU 增量` = 20.8MiB）；或插桩取 `send_stream.capacity()` 最小值 | 10 min | ≥4MiB（预期）⇒ R4 对本票收益 0，只作独立健壮性项；< 1×BDP ⇒ R4 才有资格当本票修法 |
| **E6** | 三点埋 trace（`poll_capacity` 返回值 / `poll_frame` Ready-Pending / 实际 write 字节，带时刻） | 需构建，最后做 | 直接判 H1 流控饥饿 / H2 应用供给不足 / H3 唤醒丢失（E2+E3 已能近似替代） |

## 7. 推荐排序与取舍

**执行顺序：R0（E1→E2→E4→E5） → R1（若 E4 符号为正） → R5（顺手，零回归） → R2 → R6（仅当 E2/E3 指向写侧唤醒） → R3（最后，且必须可回滚）**

**明确否决**：
- 直接把 R4（vendor h2 改退款）当本票修法 —— 窗余量 8.7×，投入 1-2 人日换 0 收益；
- 先动手改代码再测 —— rig 有 1.86× 双稳态，盲改等于把噪声当信号。

**R4 的正确归宿**：作为**独立健壮性项**立项（「任意 RTT 下不饿死 + WU 帧数比 Go 少 2-3 个数量级」），触发条件是 `窗 < 1.5×BDP` 的部署形态（60MB BDP 级），与本票解耦。这条是「比 Go 更好」的真正落点，但要等 zct77 收口后再开。

## 8. 反例 / 陷阱清单（每条一句话判死）

| # | 诱惑 | 理由 |
|---|---|---|
| 1 | `max_send_buf` 调到 64MiB | 加深囤积，把停-倒相位拉得更极端 |
| 2 | 「每写即 flush」 | hyper 每次 `send_data` 后连接任务就写，额外 flush 不产生新在网字节（M5） |
| 3 | `TCP_NOTSENT_LOWAT` | 只限未发送队列深度，不提在途；大 BDP 下反而增加 syscall |
| 4 | 缩流窗「让退款更勤」 | h2 的阈值与地板都与窗同比例缩（地板 2W/3），在途需求=BDP 不变 ⇒ 只降天花板（RJZW2 实测缩窗 ≤26MB 掉 14-31%） |
| 5 | 对齐 Go 的 3.8KB 细写 | 写粒度不是瓶颈：ours 57KB/写反而更快；C≈D 也证 Go 客户端打我们服务端不快 |
| 6 | 先上 vendor h2 做低水位退款指望救 7.77 | 窗地板是需求的 8.7×；先做 E1 |
| 7 | 打开 hyper `adaptive_window` | h2 0.4.20 根本没这个能力（M3），前班报告此处有误 |
| 8 | 单轮 A/B 下结论 | 已实测同配置 7.77 vs 14.48（1.86×），必须 3 轮交错 + 中位 + 失速占比 |
| 9 | 把内存池/清零/分配当嫌疑 | 与 1-RTT 周期无因果；分配站点已归因（z02z8/zct77 表） |
| 10 | 信 netem 默认 `limit 1000` | 150ms×1000 包即丢包，是 ±3x 方差来源；必须 `limit 50000` 且每轮查 drops |
| 11 | 照搬 Go 的连接窗自适应翻倍 | Go 靠 PING/PONG 估 BDP；我们连接窗已 ≫BDP，扩缩都不动 7.77 |
| 12 | 「加并发流互相覆盖退款」当吞吐手段 | 先由 E1 证明单流被窗卡；单核下多流摊薄 CPU（bd bhneq） |
| 13 | 只改一侧就宣布收工 | 必须 A 上升**且 C 不下降**，否则只是把瓶颈搬到另一侧 |

## 9. 验收

1. 同机对拍 ours-server / Go-server **≥0.85x@RTT308ms**（票面）；用户目标「做得比 Go 好」= **>1.0x**。
2. 0ms 不回退（≥0.95× 现基线 64 MB/s）。
3. 修法必须让 **A 上升且 C 不下降**（矩阵双格判据）。
4. 每项改动带前后 A/B（3 轮交错、中位、失速秒占比、离散>15% 重跑）。
5. 真机白天 v2rayN 测速 xhttp-cdn ≥45MB/s（需真机窗口，另行安排）。

## 10. 风险

- **rig 双稳态未排除**：若 E2 证明快慢轮窗差异显著，则历史上所有单轮 A/B 结论（含票面 0.51-0.66x）都需以「同稳态对比」方式复核。
- **R1 方向未知**：E4 之前落常量有 50% 概率反向。
- **R6 与框架纪律冲突**：自持 h2 写泵属新机制，按 §3.5.3 必须先落 `xray-frame` 或逐条举证例外，不能留在协议 crate。
- **单核 VPS 上限**：us1 `nproc=1`，xhttp+REALITY 服务端 CPU 上限 ≈33MB/s（bd bhneq）——本票在 us1 的绝对天花板受此约束，验证要区分「协议缺陷」与「CPU 上限」。

## 11. 外部先例与两份独立分析的差异（必读）

### 11.1 两份分析的冲突 —— 由实验裁决，不许挑一个信

| | `oracle`（设计咨询） | `H2FlowResearch`（源码取证） |
|---|---|---|
| 结论 | 流控**不是**主因：窗地板 20.8MiB = 需求的 8.7× | 流控**是**主因：空转笔数 ≈ 退款笔数 = `105.5MB / 11.18MB ≈ 9.4 笔 × 0.308s = 2.89s`，与 strace 实测 `2.89s / 8.41s = 34%` **在 1% 内吻合** |
| 关键机制 | 停-启相位灌装 + kernel autotune 双稳态 | **死区**：`capacity = min(窗余量, max_send_buf − buffered)`；当 `available ≤ M` 时写入让两项同减 ⇒ capacity 不回升，只能等 WU（`h2/src/proto/streams/stream.rs:282-295`、`:303-336`） |
| 修法方向 | 缩 `send_buf`（但符号待 E4） | ① `T ≥ 1.5×BDP`（本机 0ms 64MB/s ⇒ BDP≈19.7MB ⇒ T≥29.6MB；现 32MiB 只剩 8% 余量）② **`send_buf` 必须远小于对端最小额度（建议 4MiB；调到 32MiB 应更糟）** |

**分歧的实质**：**「窗余量充足」≠「发送端有 capacity」**。死区机制让「buffered 顶满 16MiB」本身把 capacity 压到 0，与窗余量无关 ⇒ 两个结论可同时成立。
**裁决实验 = E4**（`send_buf` 2M/5M/16M 三档）：变好 ⇒ 死区说成立（librarian 对，落 1 行常量）；单调变坏 ⇒ 唤醒成本说成立（转 R6）。**两方都对一半也是可能的：先 E4，再看残差用 E2/E3 分层。**

### 11.2 h2 退款额度精确解（已数值校验）

稳态解 `unclaimed = 剩余窗/2` ⇒ 每笔退款增量 = **T/3**。`T=32MiB` → `11,184,810 B`；票面四笔实测 `11,182,143 / 11,173,888 / 11,452,416 / 11,223,107` **全部落在 `[T/3, T/3+16KiB)`**。
⇒ 稳态窗地板 = **2T/3**；要「永不跌穿 BDP」需 **T ≥ 1.5×BDP**。

### 11.3 外部先例（每条一句话）

- **RFC 9113 §5.2.3**：窗口必须始终 > BDP，否则流控直接限吞吐；§6.9.1 鼓励激进补窗。
- **h2#976**：低于阈值的已退额度**永不重检**（上游 master 仍在）——这解释了退款节律的刚性。
- **h2#975**：双端 `adaptive_window` + 控制帧可**死锁**（0.4.19/0.4.20 可复现，12 次中 4 次）。
- **nghttp2#1722**：窗粒度错配使 0.33s 变 38s；维护者口径「窗取 BDP、按半窗补」。
- **gRPC-Go（2017）**：BDP 自适应 + 读写解耦 + 蹭包退款，高延迟下「order of magnitude」级改善——R4 的外部同构。
- **hyper#3338**：`stream capacity is 0` 卡死的实测样本。
- **无反例**：以「阈值选择」为变量的同行评审论文 **查无**（标注不虚构）。

### 11.4 对外部实现的可套用性

- **可直接套**：①窗取 `1.5×BDP` 以上 ②`send_buf` 降到 ≈4MiB（远小于对端最小额度）。
- **不适用**：Go 的「连接级额度在 DATA 到达时就退（与应用读解耦）」、quinn 的「窗的固定 1/8」、Go 的「按 avail 切帧」——**三者都在 crate 内，h2 无 hook**（阈值是 private const，全 crate 仅一处，无 feature 开关）。
- **最后手段**：fork h2 改阈值（`flow_control.rs:24-25`）——本仓有 `vendor/rustls`、`vendor/quinn-proto` 先例，但 rebase 成本月度级。

### 11.5 对 R4（原创低水位退款）的最终定位

外部同构 = gRPC-Go 的解耦 + 蹭包退款；设计成立（WU 帧 18/100MB vs Go 约 6.4×10³），**但对本票收益为 0 或未知**（取决于 E4/E5）。**作为独立健壮性项立项，不塞进 zct77。**

## 12. 实验结论（2026-11-09 实测，**两条路线已判死**）

WSL rig（netem 150ms、本地 origin、交错 3 轮/档、中位、`tc -s qdisc` drops 全 0、离散 ≤5.5%）：

**E1 — 客户端流窗（判流控）**

| 档 | 中位吞吐 |
|---|---|
| 4MiB 流窗 | **7.84 MB/s**（比基线降 13%） |
| 32MiB（基线） | 9.05 MB/s |
| 64MiB 对照 | 9.23 MB/s（≈基线） |

⇒ **流控/退款策略正式排除**：调小更差、调大无收益。**同时证伪** §11 里 librarian 的两条推论——「`T ≥ 1.5×BDP` 才能不饿死」（64MiB = 2×BDP 仍无提升）与「死区（send_buf 顶满压 capacity）」作为主因（见 E4）。oracle 的算术结论（窗余量 8.7×）**成立**。

**E4 — 服务端 send_buf（判死区/唤醒成本）**

| 档 | 中位吞吐 |
|---|---|
| 2MiB | 8.87 MB/s |
| 5MiB | 9.14 MB/s |
| 16MiB（现状） | 8.91 MB/s |

⇒ **三档全平（差 <3%，噪声内）**：R1 判死；且 2MiB 未劣化 ⇒「capacity 归零唤醒成本是主项」的反向结论**也不成立**。

**累计已判死的静态参数面**：10 组窗扫描（历史）+ 本轮 6 档 = **16 组全平或更差** ⇒ 改窗常量、改退款粒度、改 send_buf **三条路全部关闭**。

**⚠️ 尚未验证的关键前提**：本轮基线是 **WSL rig 的 9.0-9.3 MB/s**，而票面的「ours 7.77 vs Go 14.9」是 **VPS** 数字。⇒ **1.9× 差距在本 rig 上从未被复现**。下一步必须先跑「同 rig 四格矩阵」（实验 M），确认差距是否复现：
- 复现 ⇒ 继续 E2（`ss -tinm` 三态）/ E3（pcap 判唤醒饥饿）；
- 不复现（A≈B）⇒ 现象是 **VPS 单核特有**（CPU/单核调度），必须转 VPS 专项，不在 WSL 上调代码。
