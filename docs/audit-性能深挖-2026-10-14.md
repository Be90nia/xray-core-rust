4. **③ 修复路径到 API 级**：hyper-1.10.1 server Builder **已有** `initial_stream_window_size`/`initial_connection_window_size`/`adaptive_window`（http2.rs:157/170/183），hyper-util 0.1.20 auto Http2Builder 全量直通（mod.rs:971/981/991）——**transport.rs:233 链上加两行即修，无需升级版本、无需 patch**。修复注意次级钉：客户端 `max_send_buf_size(4MB)`（dialer.rs:569）修后成为新钉（4MB/RTT@169ms≈23.7MB/s，低于 25 判据），须同批上调。

## 2. W3：gRPC 出站 64KB 流窗（来源 + wire 应用双确认）

### 2.1 64KB 的确切来源（静态链，每环 file:line）

1. `crates/xray-transport-grpc/src/config.rs:30-31`：`#[derive(Debug, Clone, Default, ...)] pub struct Config` → `initial_windows_size: i32`（:46，注释「0 表示用默认值」）**缺省 = 0**。
2. `config.rs:86-88`：`get_i32 = ... .unwrap_or(0)` —— settings JSON 在但 `initialWindowSize` 字段缺省 → **0**；settings 整体缺失 → `Config::default()`（:66-68）→ **0**。
3. `transport.rs:152-155`：`if cfg.initial_windows_size > 0 { builder.initial_window_size(...) }` → 0 → **setter 跳过**。
4. h2-0.4.19 `src/client.rs:705-708`：`initial_window_size(&mut self, size)` → `self.settings.set_initial_window_size(Some(size))`；settings 字段即「Initial Settings frame to send as part of the handshake」（:334-335）。
5. `client.rs:1353-1356`（handshake2）：`codec.buffer(builder.settings.clone().into())` —— builder.settings **原样序列化进 wire SETTINGS 帧**。未设时该参数缺位 → RFC 9113 缺省生效。
6. RFC 缺省常数：h2-0.4.19 `src/frame/settings.rs:43-44`：`/// The default value of SETTINGS_INITIAL_WINDOW_SIZE` `pub const DEFAULT_INITIAL_WINDOW_SIZE: u32 = 65_535;`
7. 连接级同钉：`initial_connection_window_size`（client.rs:740-743）未设 → 连接窗目标缺省 65,535（client.rs:1395-1399 doc「The default value is 65,535」）。

**结论**：64KB 来源 = **RFC/协议缺省 65535（经 h2 常数显式化）**，非 hyper（grpc 链路不经过 hyper client——`transport.rs:15 use h2::{client, server}`）。R1 W3 表中「hyper client 默认 2MB（hyper-1.10.1 client.rs:49）」常数本身存在（hyper client proto/h2/client.rs:48-49 conn 5MB/stream 2MB）但对 grpc 不适用，**路径纠错如执行摘要 #3**。

### 2.2 wire 实证 + 动态吞吐（RTT=50ms）

| 组 | client 配置 | wire SETTINGS 0x4 | 下载实测 |
|---|---|---|---|
| D1 | 裸 `Builder::new()`（= 产品 settings 缺失/字段缺省路径） | **None**（参数缺位） | **0.9 MB/s** |
| D3 | 显式 `initial_window_size(65535)` | **Some(65535)** | **0.9 MB/s（≡D1）** |
| D2 | `initial_window_size(16MB)+initial_connection_window_size(32MB)` | **Some(16777216)** | **224.8 MB/s（250×）** |

生产量级：64KB 窗 @169ms ≈ 65535/0.169 ≈ **0.37-0.39 MB/s**——R1 数字成立。「是否真应用到 wire」：设了就出现在 SETTINGS（0x4=value），没设就缺位走 RFC 缺省，两条路径等效钉在 64KB。

Go 对照（grpc-go）：`initialWindowSize` 缺省同为 64KB 量级，但 grpc-go 有 **BDP 估计器动态扩窗**（bdpPing，上限 16MB）——h2 crate 无接收侧自适应（`adaptive_window` 是 hyper 侧封装，grpc 链路未用）→ Go 同协议无此钉、Rust 有，修复应显式大窗（16MB/32MB 对齐 enc8x 形态）或补 BDP 自适应（工程量大，不推荐本轮）。

### 3.2 W2 修复可行路径（修复到方案级，本轮未改产品代码）

- **首选（一行链式）**：`transport.rs:233` 的 `.max_send_buf_size(16 * 1024 * 1024)` 后加

## 6. 局限与疑虑（DONE_WITH_CONCERNS）

1. **机制级证明**：delay pipe 是合成传播延迟（带宽无限、缓冲无限），证明的是「窗 ÷ RTT 钉子存在且 setter 解除」的因果，不给出生产绝对 MB/s；生产数字仍以 v2rayN 同窗实测为唯一验收（memory 判据不变）。
2. **RTT 换算的外推**：169ms 生产 RTT 下的期望值（5.9/0.37/23.7 MB/s）是线性外推，未实测（禁 SSH VPS 契约）。
3. **U-B/B2/D2 达成率 63-74%**：快组未到理论 335MB/s——管线（Mutex 队列 + 定时器唤醒）与 h2 WINDOW_UPDATE 粒度开销，组间同栈可比性不受影响。
4. **W4 QUIC/h3 未做**（契约时间盒）；R1PERF-004/005 分配残留的 alloc 次数量化未做（非本轮任务书项）。
5. 首轮 D3 曾因实验代码自身 bug（conn 窗传 0）挂起，已修复并全量复跑 D 组；U 组数字为首轮原值（未受影响）。
